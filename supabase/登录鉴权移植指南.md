# 登录鉴权加固移植指南

> 本指南源自 EasyAPI(Next.js 16 + Supabase)项目已完成并验证的登录鉴权加固,
> 适用于登录逻辑基本一致的 better-nav 项目。
> 实施前请先通读全文,按文件逐个对照移植。

---

## 一、背景与目标

**场景**:网站为站长个人使用,后台数据由站长自己管理。

**原始风险**:
1. 登录页开放公开注册 + GitHub/Google OAuth,任何人注册即可登录,登录后即可对后台数据增删改查;
2. 前端代码里 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 公开可见,若 Supabase 表未启用 RLS(行级安全),攻击者可绕过应用层直接调 Supabase REST API 增删改数据。

**目标**:三层白名单鉴权 + 数据库 RLS 兜底,只允许 `ADMIN_EMAILS` 中的邮箱管理后台。

| 层 | 措施 |
|---|---|
| API 层 | 增/删/改接口校验"登录 + 邮箱白名单",未通过返回 401 |
| 页面层 | `/admin` 页面服务端渲染前校验管理员,未通过 redirect 到登录页 |
| 中间件层 | 未登录或非白名单访问 `/admin`,302 到 `/login` |
| 数据库层 | Supabase RLS:anon 只读,仅白名单邮箱可写 |

---

## 二、技术前提

- Next.js(App Router)+ `@supabase/ssr` / `@supabase/supabase-js`
- 环境变量:`NEXT_PUBLIC_SUPABASE_URL`、`NEXT_PUBLIC_SUPABASE_ANON_KEY`
- **新增环境变量**:`ADMIN_EMAILS`(管理员邮箱白名单,逗号分隔多个,大小写不敏感)

## 三、改动清单(按文件)

### 1. 服务端工具函数:新增 `requireAdmin()`

文件:`src/lib/supabase/server.ts`(EasyAPI 路径,下同;better-nav 按自身结构对应)

在已有 `requireUser()` 旁新增:

```ts
/**
 * @description: 校验管理员：登录 + 邮箱白名单（ADMIN_EMAILS，逗号分隔），
 * 不满足任一条件返回 null（后台写操作接口鉴权用）
 */
export async function requireAdmin() {
  const user = await requireUser()
  if (!user?.email) {
    return null
  }
  const adminEmails = (process.env.ADMIN_EMAILS || '')
    .split(',')
    .map(email => email.trim().toLowerCase())
    .filter(Boolean)
  if (!adminEmails.includes(user.email.toLowerCase())) {
    return null
  }
  return user
}
```

> 依赖的 `requireUser()`:
> ```ts
> export async function requireUser() {
>   const supabase = await getSupabaseServerClient()
>   const { data: { user } } = await supabase.auth.getUser()
>   return user
> }
> ```

### 2. 写操作 API 路由:改用 `requireAdmin()`

对后台数据的所有 **POST / PUT / DELETE** 路由(EasyAPI 中为 apis、categorys 两套资源),把原来的登录校验换成管理员校验:

```ts
// 校验管理员（登录 + 邮箱白名单）
const user = await requireAdmin()
if (!user) {
  return NextResponse.json(responseMessage(null, '未登录或无权限', RESPONSE.ERROR), { status: 401 })
}
```

同时把 import 改为:
```ts
import { getSupabaseServerClient, requireAdmin } from '@/lib/supabase/server'
```

**注意**:`GET`(查询)接口保持公开,因为首页/接口列表需要对外展示。若 better-nav 的后台列表也不需要对公网公开,可自行决定是否也加校验。

### 3. 后台管理页面:服务端校验管理员

文件:`src/app/admin/page.tsx`。页面组件改为 async,渲染前校验:

```tsx
import { redirect } from 'next/navigation'
import { requireAdmin } from '@/lib/supabase/server'

const Admin: FC = async () => {
  const admin = await requireAdmin()
  if (!admin) {
    redirect('/login')
  }
  return (/* 原有内容 */)
}
```

### 4. 中间件:`/admin` 白名单拦截

文件:`src/lib/supabase/proxy.ts`(EasyAPI 用的是 Next 16 的 proxy;若是 middleware.ts 同理)。在更新 session 的逻辑中:

```ts
const { data } = await supabase.auth.getClaims()
const claims = data?.claims

// 管理员白名单（与 requireAdmin 保持一致）
const adminEmails = (process.env.ADMIN_EMAILS || '')
  .split(',')
  .map(email => email.trim().toLowerCase())
  .filter(Boolean)
const email = typeof claims?.email === 'string' ? claims.email.toLowerCase() : ''
const isAdmin = !!(email && adminEmails.includes(email))

// 已登录访问登录页：管理员跳管理页面，其他用户回首页
if (claims && path.startsWith('/login')) {
  return NextResponse.redirect(new URL(isAdmin ? '/admin' : '/', request.url))
}

// 未登录或非白名单邮箱访问管理页面，一律跳登录页
if ((!claims || !isAdmin) && path.startsWith('/admin')) {
  const url = request.nextUrl.clone()
  url.pathname = '/login'
  return NextResponse.redirect(url)
}
```

> 说明:此处沿用 `getClaims()`(读 JWT 声明,不验签,性能好)。若追求更严谨可改用 `supabase.auth.getUser()`(会发网络请求),按项目对中间件性能的要求取舍。

### 5. 登录页:隐藏"立即注册"入口(可选但推荐)

`src/app/login/ClientComponent.tsx`:
- 删除 `isSignup` 状态、注册/登录切换 UI、"立即注册"链接;
- 表单提交直接调用 `supabase.auth.signInWithPassword(data)`(删除 `signUp` 分支);
- OAuth 按钮按需求保留或移除(若保留,白名单会兜底)。

### 7. 数据库层兜底:RLS 策略

> 📌 本节记录的是当初手工加固的过程。现在 RLS 策略已并入初始化脚本 `supabase/schema.sql`(第 5、6 段),新项目直接跑那个脚本即可;下面的写法保留作原理参考。

新建 `supabase/rls.sql`,在 Supabase Dashboard → SQL Editor 整段执行(先把 `you@example.com` 换成自己的邮箱):

```sql
-- ============================================================
-- 行级安全（RLS）兜底策略
-- 作用：即使有人拿到浏览器里公开的 anon key 直接调用
-- Supabase REST API，也无法绕过应用层增删改数据。
-- ============================================================

-- ---------- 1. 主表（按实际表名替换，如 ea_apis） ----------
ALTER TABLE public.ea_apis ENABLE ROW LEVEL SECURITY;

-- 清理该表上所有既有策略，避免旧的宽松策略残留放行匿名写
DO $$
DECLARE pol RECORD;
BEGIN
  FOR pol IN
    SELECT tablename, policyname FROM pg_policies
    WHERE schemaname = 'public' AND tablename = 'ea_apis'
  LOOP
    EXECUTE format('DROP POLICY IF EXISTS %I ON public.%I', pol.policyname, pol.tablename);
  END LOOP;
END $$;

-- 公开可读（首页 / 列表展示需要）
DROP POLICY IF EXISTS "ea_apis_public_read" ON public.ea_apis;
CREATE POLICY "ea_apis_public_read"
  ON public.ea_apis FOR SELECT
  USING (true);

-- 仅管理员可写
DROP POLICY IF EXISTS "ea_apis_admin_write" ON public.ea_apis;
CREATE POLICY "ea_apis_admin_write"
  ON public.ea_apis FOR ALL
  USING (auth.jwt() ->> 'email' IN ('you@example.com'))
  WITH CHECK (auth.jwt() ->> 'email' IN ('you@example.com'));

-- ---------- 2. 第二张表（按实际表名重复上述步骤） ----------
-- ALTER TABLE public.ea_categorys ENABLE ROW LEVEL SECURITY;
-- ...（同上：清理旧策略 + public_read + admin_write）
```

> ⚠️ **关键**:策略是 OR 合并语义——表上若残留旧的宽松策略(如 `..._for_all_users`、无条件的 UPDATE/DELETE 策略),新建的限制策略不会生效。所以必须先 DROP 全部旧策略再重建,如上 DO 块所示。
>
> ⚠️ 若表上有 `security invoker` 的 RPC(如调用计数 `increment_call_count`)在 RLS 开启后失效,将其改为 `SECURITY DEFINER` 执行即可:
> ```sql
> ALTER FUNCTION public.increment_call_count SECURITY DEFINER;
> ```

## 四、验证步骤(建议按序执行)

**A. 应用层(本地 dev server)**

1. 未登录 `POST` 任一写接口(如 `/api/apis`),应返回 `401 未登录或无权限`:
   ```powershell
   Invoke-WebRequest -Uri http://localhost:3000/api/apis -Method Post -Body '{}' -ContentType 'application/json'
   ```
2. 未登录访问 `/admin`,应 302/307 重定向到 `/login`。
3. 用**不在白名单**的账号登录 → 访问 `/admin` 仍被弹回;手动调写接口返回 401。
4. 用**白名单**账号登录 → 正常进入后台增删改查。

**B. 数据库层(直接调 Supabase REST API,模拟拿 anon key 的攻击者)**

从 `.env` 取 URL 与 ANON_KEY,对每张表测试:

1. **匿名读**:`GET {URL}/rest/v1/<table>?select=id&limit=1` → 200,能读到(公开读)。
2. **匿名插入**:`POST {URL}/rest/v1/<table>` body `{"name":"__test__"}` → 应 **401**。
3. **匿名更新**:`PATCH {URL}/rest/v1/<table>?id=eq.<真实id>`,body 为原值,header 带 `Prefer: return=representation` → 应返回**空数组(更新 0 行)**。

> ⚠️ **重要陷阱**:不要用"不存在的 id"测 UPDATE/DELETE 来判断 RLS!PostgreSQL 对不存在的行执行 UPDATE/DELETE 时**总是返回 0 行成功(204)**,RLS 根本不会被评估——该测试无法区分拦截与否,容易误判"RLS 没生效"。可靠的信号是 **INSERT 返回 401** 以及 **对真实行 UPDATE 后返回 0 行**。

## 五、注意事项汇总

1. **注册通道**:前端隐藏注册入口后,Supabase 端仍可注册(邮箱验证)。彻底关闭请到控制台 **Authentication → Providers → Email** 取消勾选 *Allow new users to sign up*(可选,白名单已兜底)。
2. **OAuth**:GitHub/Google 登录若保留,登录后仍需邮箱在白名单才能进后台;白名单比对的是 OAuth 账号绑定的主邮箱。
3. **`.env` 勿提交**:含 Supabase key 与管理员邮箱,已 gitignore。
4. **RLS 执行要整段跑完**:若中途失败,表会处于"无任何策略"状态(连公开读都会被拒),重跑全文即可。
5. **修改 `.env` 后需重启 dev server** 才生效。
